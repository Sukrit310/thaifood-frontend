# Backend role-management static audit

Audited public Backend source at pinned revision [`a8c0d78f76220f596a1646913685021ccfdc83f8`](https://github.com/Sukrit310/thaifood-backend/tree/a8c0d78f76220f596a1646913685021ccfdc83f8). This is a read-only code and test review. No known blocking defect was identified in the supported API role-update path. Runtime results from Go 1.27.4 and disposable PostgreSQL 17.12 are recorded separately by the verification runner; this audit does not claim that those commands passed.

- **Authorization and concurrency:** [`UpdateMemberRole`](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/store/members.go#L35-L82) starts a READ COMMITTED transaction, acquires a PostgreSQL `SHARE ROW EXCLUSIVE` table lock before reading roles, rechecks the actor after obtaining the lock, and commits the role update atomically. This serializes role updates across API instances. No lock-order cycle is apparent among these role-update transactions.
- **Last-admin nuance:** [Self-change rejection and the actor recheck](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/store/members.go#L37-L71) preserve at least one existing admin through this API: when an authorized actor changes another admin, two distinct admins must exist under the lock. Consequently, the additional `admins <= 1` / `ErrLastAdmin` branch cannot be reached under the current valid-table/API rules. The [`409 LAST_ADMIN` handler test](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/handler/member_roles_test.go#L160-L180) uses a mocked store error; it is not evidence of a real database request returning that status. [Backend documentation explicitly states this distinction](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/docs/ADMIN_ROLE_MANAGEMENT.md#L43-L49). Privileged direct SQL after the transaction ends is outside that API invariant.
- **Existing tokens:** [Authentication reloads the database member on each request](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/mw/auth.go#L43-L59). [HTTP tests](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/integration/member_roles_test.go#L26-L50) check promotion and demotion using unchanged JWTs on subsequent requests.

The runner is executing the real PostgreSQL tests for [guards and persistence](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/store/member_roles_test.go#L28-L102), [concurrent cross-demotions](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/store/member_roles_test.go#L104-L140), [deterministic actor demotion while waiting for the lock](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/store/member_roles_test.go#L142-L191), and [HTTP cross-demotions](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/integration/member_roles_test.go#L74-L127), including repeated concurrency runs. These database suites [skip without `TEST_DATABASE_URL`](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/store/store_test.go#L20-L26), as does the [HTTP integration helper](https://github.com/Sukrit310/thaifood-backend/blob/a8c0d78f76220f596a1646913685021ccfdc83f8/integration/api_test.go#L37-L43); the runner requires zero skipped tests.

Coverage limitations: the existing suite does not explicitly exercise separate API servers/connection pools or cancellation while waiting for the table lock. Those remain untested cases, rather than identified defects.
